### Finding #2 — observation_count Mislabeled (MEDIUM) ✅ RESOLVED

**Original issue:** `buildStateSummary()` set both `observation_count` and `tool_call_count` to the same `toolCallCount` value (trace.ts old L226-235).

**Fix applied** (trace.ts:211-222):
```ts
const toolCallCount = (state.toolCalls ?? [])
    .filter((toolCall) => toolCall.step <= action.step).length;
const observationCount = (state.observations ?? []).length;

return {
    observation_count: observationCount,
    tool_call_count: toolCallCount,
    ...
};
```

**Test verification** (trace.spec.ts:5-61): Creates a synthetic state with 2 observations (one from `retrieve_tarot_knowledge`, one from `manual_review`) but only 1 tool call. Asserts `observation_count: 2, tool_call_count: 1`.

**Design note:** `observationCount` counts ALL observations without step filtering, while `toolCallCount` filters by `step <= action.step`. This means `observation_count` reflects the total observations at trace-build time, not per-step. In the common case (single retrieve step), both are 1. In multi-step scenarios, later steps will see the cumulative observation count. This is an acceptable design choice for diagnostics — the distinction would only matter if observations were added asynchronously or by non-agent-loop nodes, which doesn't happen in the current graph.

**Verdict:** Correct semantic separation. Test validates the independence.

### Finding #5 — No Diagnostic Trace for Generic Failures (MEDIUM) ✅ RESOLVED

**Original issue:** `runReadingGraphWithDiagnostics` catch block re-threw non-`ReadingServiceError` errors without a trace; `generateDraftNode` provider calls were not wrapped.

**Fix applied — four new functions in graph.ts:**

1. **`summarizeInternalErrorCause(error)`** (L193-201): Truncates and whitespace-normalizes error messages to max 160 chars. Handles non-Error objects gracefully via `String(error)`.

2. **`buildGenericGenerationError(error)`** (L203-213): Wraps in `ReadingServiceError("generation_failed", ...)`, attaches summarized cause.

3. **`throwGenericFailureWithDiagnosticTrace(error, state)`** (L215-229): Core wrapper — handles both `ReadingServiceError` (adds trace if missing) and arbitrary errors (wraps + traces). Uses `status: "failed"`.

4. **`generateDraftNode` try/catch** (L825-844): Both `generateInitialRead` and `generateFinalRead` calls wrapped. Provider failures and `requireStateValue` failures inside the try blocks are caught and traced.

5. **`runReadingGraphWithDiagnostics` catch** (L1027-1045): Builds a skeleton trace (`{ runId, traceStartedAt }`) with `status: "failed"` for graph-level failures.

**Test verification** (graph.contract.spec.ts:318-353): Provider throws `Error("planned provider failure with private draft details")` → caught → `diagnosticTrace.status === "failed"`, `run_id` present, `agent_steps` shows `["final_answer"]`.

**Edge case analysis:**
- Provider crash during `generateInitialRead` → caught by node-level try/catch → trace includes full graph state (agent_actions, observations, etc.)
- Provider crash during `generateFinalRead` → same coverage
- LangGraph internal error (e.g., serialization failure) → caught by `runReadingGraphWithDiagnostics` catch → skeleton trace with only `runId`/`traceStartedAt`
- `ReadingServiceError` thrown with existing trace → passes through `throwGenericFailureWithDiagnosticTrace` unchanged (L219-223 check)
- `ReadingServiceError` thrown WITHOUT trace (e.g., from `requireStateValue` inside provider try block) → gets `status: "failed"` trace added (L220-222)

**Verdict:** Comprehensive coverage of all failure paths. The dual-layer catch (node-level for provider failures, graph-level for everything else) is well-reasoned.

## 3. Cross-Cutting Analysis

### New Code Quality Assessment

**`summarizeInternalErrorCause` (graph.ts:193-201):**
- Regex `.replace(/\s+/g, " ")` normalizes all whitespace including newlines — appropriate for diagnostic messages
- 160-char truncation with `…` suffix — conservative, prevents long error messages from leaking into traces
- `String(error)` handles non-Error throws (`throw "string"`) without crashing

**`buildGenericGenerationError` (graph.ts:203-213):**
- The `as ReadingServiceError & { cause?: unknown }` type assertion is a pragmatic workaround for TypeScript's `ErrorOptions.cause` being ES2022. At runtime, assigning `.cause` on any object works.
- The `cause` field preserves diagnostic context without leaking full error details into the public error message.

**`throwGenericFailureWithDiagnosticTrace` (graph.ts:215-229):**
- The `if (!error.diagnosticTrace)` guard is correct — prevents overwriting an existing trace from `throwWithDiagnosticTrace`.
- Calls `buildGenericGenerationError` BEFORE assigning trace, which is the correct order (trace is assigned to the wrapper, not the original).

All unchanged functions in `graph.ts` retain their original signatures and behavior. No edge cases were removed:
- `throwWithDiagnosticTrace` — unchanged

The `generateDraftNode` change is purely additive (try/catch wrapping) — both return values under success are identical.
